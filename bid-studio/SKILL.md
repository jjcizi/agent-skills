# 标书超级工坊（bid-studio）

## Overview

本技能是**投标全生命周期的一站式超级技能**，融合统一了以下 8 个子技能的能力，并**选择性融入 kami 排版审美体系**：

| 来源 | 核心能力 | 融合后所处管线 |
|------|----------|----------------|
| 投标文件撰写（甲乙知识库版 v3.4） | 甲乙知识库前置、图片嵌入、师资填充、字数控制、转 Word | P0 / P6 / P11 |
| 标书解析（tender-analysis） | 条款级解析、反向漏检、解析总表/漏项清单/写作任务单 | P2 |
| 投标文件撰写（tender-writing v2.2.1） | 结构一次性确认、附件清单、终检双轨对照 | P4 / P5 / P6 / P10 |
| 技术方案文档撰写（technical-solution-writing） | 防缩水硬约束、评分权重分配篇幅 | P6 |
| 技术文件润色与扩写（tender-technical-refine） | 去 AI 化、自然语言段落 | P7 |
| 技术文件图表 Mermaid 规范化（tender-technical-mermaid） | Mermaid/数据图校验与转换 | P8 |
| 技术标定稿清理（tender-technical-finalize） | 剥离写作元数据、交付稿净化 | P9 |
| 投标文件审查（tender-bid-review） | 只读合规审查、否决项/评分覆盖报告 | P10 |
| **kami（选择性融入）** | 排版审美体系：配色、字体、字号层级、间距栅格、版式节奏 | P11 + 排版审美规范 |

**核心原则（贯穿全程）：**

- **先锁定、再覆盖**：多包项目先锁定到最小投标单元（叶子节点），再进入条款级/章节级工作。
- **先核对、后写作**：写每一章/节前必须回看招标文件原文（及甲乙知识库），禁止凭记忆或二手摘要泛写。
- **先扫描、后写盘**：润色、图表、定稿清理等后处理动作，默认「扫描 + 清单 + 用户确认」后才落盘，禁止擅自批量覆盖。
- **先确认范围、再动笔**：P3 选定编写哪些响应文件（商务/技术/报价）后才搭结构；P6 设定字数（万字）后才写正文。
- **先终检、后交付**：未通过终检/审查门禁，禁止宣称「已完成 / 可交付」；P11 确认输出格式后才导出 Word/PDF。
- **不编造**：客户信息、资质、业绩、参数、预算、报价、测试数据一律不得虚构；缺失用占位并集中列出待补清单。

**入口路由（本技能与单点技能的关键差异）：**

用户请求 + 工作区现状共同决定**从哪个阶段切入**，不必每次都从零开始：

| 用户意图 | 工作区现状 | 切入阶段 |
|----------|-----------|----------|
| 「写一份标书/技术方案」（有招标文件） | 空或仅有招标文件 | P1（或先 P0 选择知识库模式并建库） |
| 「写一份技术方案」（仅有简要需求，无招标文件） | 空 | P6（技术方案模式 B，跳过商务/报价/解析） |
| 「润色已有技术标 / 去 AI 化」 | 已有技术标 .md | P7 |
| 「校验图表 / 统一为 Mermaid」 | 已有技术标 .md | P8 |
| 「定稿清理 / 准备交付」 | 已有技术标 .md 且已确认可定稿 | P9 |
| 「审查已有投标文件」 | 已有投标成稿 + 招标文件 | P10（只读审查） |
| 「导出 / 排版成 Word 或 PDF」 | 已有投标 .md | P11 |

**路由规则**：进入工作区后，先扫描目录判定「是否已有投标/技术 .md」，再结合用户请求定位起始阶段；**不得**在已有成稿时假装从零重写。用户可显式指定从任一阶段开始或跳过可选阶段（P0/P7/P8/P9 均可选）。

## 输入与前提

- 能读取招标文件（PDF/Word/OCR 文本/摘录，或用户打开的文件、路径、粘贴关键章节）；无法访问时先说明并请用户补充。
- 能读取、编辑工作区内 `.md`。
- 所有产出文件建在**当前工作区**约定根目录（默认 `投标文件/`），路径用相对工作区根的写法；工作区外路径不计入交付清单。
- 可选甲乙知识库：甲方知识库（招标方战略/规划/制度/需求）、乙方知识库（投标方案/案例/能力证明/师资/资质图片）、图片库（`c:/knowledge/`）。**仅当用户启用「知识库模式」时才进入 P0 搭建，非知识库模式直接进入 P1。**

### 信息缺失处理

- 不得编造客户信息、指标、预算、报价、参数。
- 缺失信息用 `【待用户补充：xxx】` 或 `[待用户补: xxx]` 标记，并集中输出「待确认清单 / 用户待补清单」。
- 无法确定的条目必须进入 `漏项清单.md`，不得静默跳过。

## 阶段总览（P0 → P11）

|------|------|----------|-----------------|

## P0：知识库模式选择与前置搭建（可选，知识库模式专属）

> 来源：投标文件撰写（甲乙知识库版 v3.4）阶段 0。本阶段新增「知识库模式选择门禁」，让用户明确选择是否启用及选用哪类知识库。

### 0.0 知识库模式选择门禁（进入 P1 前必问）

进入投标解析/撰写前，**必须先让用户选择知识库模式与甲/乙知识库**，不得默认启用、不得默认跳过：

1. **是否启用知识库模式**：向用户提问「本次投标是否启用甲/乙知识库辅助撰写？」——默认**建议启用**（能提升甲方诉求贴合度与乙方方案复用度），但须用户明确表态；未表态不得擅自建库或直接跳过。
2. **知识库选型（用户点名环节）**：启用时请用户勾选本次使用的知识库，可单选/多选：
   - **甲方知识库**：招标方战略、规划、制度、需求说明、行业规范等 —— 用于理解招标需求、对齐甲方诉求；
   - **乙方知识库**：投标方成功案例、技术方案、能力证明、师资信息、资质图片等 —— 用于输出方案、复用案例、填充师资与图片；
   - **图片库**（`c:/knowledge/` 或工作区 `images/`）：乙方资质/师资/案例图片 —— 用于正文图片嵌入。
   用户须给出每类知识库的**实际路径或文件范围**（或明确「稍后由我导入到工作区目录」）；未指明来源的，不得声称已「读取了知识库」。
3. **乙方公司名称**：启用乙方知识库时一并请用户输入乙方公司名称（正文乙方称呼统一使用）。
4. **门禁 0-0**：未获用户对「是否启用 + 选型 + 路径」的明确回复前，不得进入 0.1 建库，也不得越过 P0 直接进入 P1；用户明确选择「不启用知识库模式」时，跳过 P0 直接进入 P1，后续正文不得引用知识库内容。

### 0.1 建库与资料体检

1. 启用知识库模式时，在工作区根目录创建：`甲方知识库/`、`乙方知识库/`、`images/`。
2. 暂停并提示用户：
   - 将甲方相关文件（战略、规划、制度、需求说明、行业规范等）导入「甲方知识库」；
   - 将乙方相关文件（成功案例、技术方案、能力证明、师资信息、资质图片等）导入「乙方知识库」；
   - 图片导入 `images/` 或指定 `c:/knowledge/`。
3. **门禁**：未收到用户「确认知识库已填充」回复前，不得进入 P1。

知识库使用规则（贯穿 P6）：仅读取不修改源文件；正文以甲方知识库理解需求、乙方知识库输出方案；图片优先从乙方知识库/图片库提取，无则网络补充（存 `images/`），核心信息无匹配保留占位、绝不编造。

## P1：招标文件识别与分包锁定（投标场景门禁 0）

> 来源：tender-writing 文件识别门禁 + tender-analysis 阶段 0

### 1.1 文件识别与复核

1. 全文件检索 `招标公告`、`投标人须知`、`评标办法`、`投标文件格式` 等核心章名；命中任意 2 项，不得判为「非招标文件」。
2. 长文档至少抽检首段 + 中段 + 尾段，禁止仅凭前部技术说明下结论。
3. 用户纠正「这就是招标文件」时，重跑检索并列出命中证据再更新结论。
4. 输出三行：`已命中章节` / `识别结论` / `下一步`。

### 1.2 分包与目标包锁定

1. 通读「分包」「标段」「包件」「合同包划分」「采购需求」「分册」，判断是否多包/多标段。
2. **多包且用户未指明**：必须先**完整列出所有可选包**（包号、包名、一行范围摘要），再向用户提问，由用户确认**包号或包名称**。
3. **子包/分项**：若选定大包下仍有「子包/分项/品类分组」，继续展开到**最小投标/解析单元（叶子节点）**；用户仅确认大包未确认子包时，不得进入 P2。
4. **单一包或用户已指明**：记入锁定记录即可。

**锁定记录（必写）**：`投标目标 = {项目名} / {包号或包名} / {子包如有}`，后续所有产物命名与引用须与此一致。

**门禁 0**：未锁定最小投标单元前，禁止进入 P2 及以后。

## P2：条款级解析（投标场景门禁 1）

> 来源：tender-analysis 阶段 1-5 + tender-writing 阶段 A

### 2.1 范围锁定与资料体检

1. 锁定解析对象：项目名、已确认包件/标段、版本号、发布日期。
2. 资料完整性检查：招标公告、投标人须知、评标办法、技术规范、格式范本、附件/附录（与锁定包相关部分）；是否缺页、乱码、扫描不可读、表格截断。
3. 输出「资料体检结论」：可直接解析项 / 需用户补充项。
4. **门禁**：资料缺失影响实质判断时，先进入待补充，不得宣称「已完成解析」。

### 2.2 章节骨架扫描（仅建索引）

扫描并列出锁定包相关范围内的一级/二级章节，单独标记高优先区：资格条件、评标办法与评分细则、否决投标/废标条款、投标文件格式与签章要求、技术参数与偏离表、**报价要求（开标一览表/分项报价表/投标函报价）**、工期/交付/验收/SLA 条款、附件/附录/脚注/备注。产出章节索引草表。

### 2.3 条款级深度解析（核心）

按「章节 → 条款 → 子项」逐层下钻，每条结构化记录到 `解析总表.md`，字段至少含：`编号 / 来源位置（章/节/条/页）/ 要求类型（硬性/评分/格式/证据/时效/否决/报价）/ 原文摘要 / 执行动作 / 目标文件 / 状态 / 风险等级`。

类型判定：硬性（必须/应当/不得/否则无效）、评分（对应分值）、格式（模板/签章/份数/命名装订）、证据（资质/业绩/授权/检测报告）、时效（报名/答疑/递交/工期/响应时限）、否决（触发废标/无效/不予评审）、报价（金额/计价方式/最高限价/分项/税率）。

**废标/否决项必须逐条分析**，产出「废标/否决项逐条分析表」：`条款原文 / 触发条件 / 我方状态（满足-风险-待补）/ 补救动作`。

**废标项分类框架（12 大类，逐类排查防漏）**：除逐条分析招标文件明示的否决条款外，还须按下列 12 大类**主动排查**招标文件是否隐含废标条件（明示条款之外的隐性否决点），避免遗漏：

1. **资质资格类**：资质证书等级不符/过期/未年检、未按要求提供、人员资格不满足、联合体资质不符。
2. **业绩证明类**：业绩金额/数量/时间不满足、无法证明、证明材料不符要求。
3. **报价类**：超最高限价、低于成本、报价不一致（大小写/开标一览表与分项报价表）、未按报价格式、税率/计价方式错误、漏报项。
4. **格式范本类**：未使用规定范本、缺少必要文件、目录/页码/份数不符、文件顺序不符。
5. **签章类**：漏盖章、漏签字、签字人无授权、公章与单位名称不符、电子签章无效。
6. **密封装订类**：未密封、密封不符（骑缝章/封条）、装订方式不符、未标注项目名称/投标人名称。
7. **时限类**：逾期递交、未按时参加开标/澄清、投标有效期不足、未按时缴纳保证金。
8. **技术实质性偏离**：带 ★ 号条款不响应、关键技术参数负偏离、供货范围/交付物不符、工期/质保期偏离。
9. **商务实质性偏离**：付款条件、合同条款实质偏离、偏离表填写不符、服务承诺不符。
10. **投标保证金**：未缴纳、金额不足、形式不符、有效期不足、保函格式不符。
11. **串通投标/弄虚作假**：围标串标、虚假资质/业绩材料、伪造证书、同一投标人提交多个报价。
12. **其他法定否决**：联合体协议缺失、未响应实质性要求、备选方案违规、法定代表人身份证明/授权委托书缺失。

### 2.4 反向漏检（防漏核心）

必须执行五项反向核查：评分反查、否决反查、交叉引用反查、附件/脚注反查、一致性反查（同一指标不同章节是否冲突，含报价与限价一致性）。任一不通过 → 回到 2.3 补提取，不得结束。

### 2.5 产物落地

必交付三件（可合并为同一文档分节呈现，但须齐全可追踪）：

1. `解析总表.md`
2. `漏项清单.md`
3. `写作任务单.md`（任务编号/来源条款/归属【商务|技术|报价】/目标章节或节文件/完成标准/依赖材料/状态）

若启用知识库模式，解析结果须额外融合：甲方核心诉求清单、乙方匹配资源清单、待深化标题/要点清单、图表规划、师资类型/数量要求、待嵌入资质图片清单。

**门禁 1**：三件中间件至少具备可执行初稿，且无「未归属条款」「未分类评分点」，方得进入 P3。

## P3：响应范围选择（商务 / 技术 / 报价，新门禁）

> 本阶段为新增门禁：结构拟定前，必须先让用户选定本次要编写的响应文件范围。

### 3.1 三大部分定义

投标文件通常由三大部分组成，对应招标文件「投标文件组成/响应文件格式」中的分册要求：

| 部分 | 常见内容 | 写作规则 |
|------|----------|----------|
| **商务响应文件** | 投标函、法定代表人身份证明、授权委托书、资格证明、业绩、承诺书、商务条款偏离表等 | 严格照搬招标格式范本，只填空不扩写 |
| **技术响应文件** | 技术方案、组织架构、实施计划、服务方案、技术条款偏离表、师资（如需）等 | 防缩水硬约束 + 评分权重分配篇幅 |
| **报价响应文件** | 开标一览表、分项报价表、投标函报价、报价说明等 | 按招标报价格式与计价规则，金额不编造 |

### 3.2 选择流程（必须先问后建）

1. 向用户列出三大部分及其将覆盖的章节清单（来自 P2 解析结果），明确说明各部分的默认内容范围。
2. **请用户勾选本次要编写的部分**：可单选、可多选、可全选（默认建议全选，除非用户明确只要某一部分，如「只写技术标」）。
3. 记录用户选定结果，作为 P4 结构拟定与 P6 正文撰写的**范围边界**：未选中的部分不搭目录、不写正文、不在终检中要求（但 P10 会提示「本部分未包含，是否确认为用户有意省略」）。
4. 若招标要求商务/技术/报价**合并成单一册**（不分册），仍按三部分内容归类提示用户选择，但目录按招标规定的单层结构组织。

**门禁 2**：未获用户选定编写范围前，禁止进入 P4 结构拟定。用户后续要求增删范围时，重新回到本阶段确认，再调整结构与任务单。

## P4：结构拟定与一次性确认（章 + 节）

> 来源：tender-writing 阶段 B + technical-solution-writing 阶段 2

### 4.1 执行顺序（先问后建）

1. 拟定结构草案（**只展示，不落地**）：仅覆盖 **P3 选定范围**内的章级目录草案（商务/技术/报价各章文件清单）+ 技术文件节级草案（每节标题 + 来源标注）。
2. **一次性结构确认**：同时向用户确认章结构与节结构。
3. **确认后再搭建**：仅用户明确确认后，才创建章级占位文件与技术节文件。

**硬约束**：未获用户确认前，禁止创建任何章文件、节文件或目录树；仅允许展示拟建清单。

### 4.2 技术节拆解规则

节标题来源优先级（从高到低）：① 招标「技术要求/技术规范书/用户需求书」条目划分；② 招标「评分办法」评分点（**每个评分点至少对应一节**）；③ 招标「投标文件格式」子条目；④ 行业强制规范必含子项；⑤ 以上均无 → 技术合理性草案，标注「招标文件未指定，为草案」。

节结构要求：层级编号（`1.1`）；每节标注来源类型 `[招标]`+条款号 / `[规范]`+规范号 / `[草案]`+依据；评分要点全覆盖；无依据的节一律不列；确认落地后不得回退为单一技术总文件、不得重复发起节结构确认。

严格禁止：❌ `[草案]` 伪装 `[招标]`；❌ 合并/拆分招标条款（除非招标原本如此）；❌ 引用同行标书、历史模板作来源依据。

### 4.3 目录规则

- 在 `投标文件/`（或用户指定根名）下组织：分册时建 `商务文件/` `技术文件/` `报价文件/`（如需报价分册），**最多三个**业务子目录且须与 P3 选定范围一致；不分册时只建一层目录。
- **一章一独立 `.md`**（章节划分以招标「投标文件格式/响应文件组成」为准）。
- 技术文件默认**一节一 `.md`**，禁止仅一个技术总文件内用二级标题代替节文件；可保留章级索引页。
- 无实质文字的章节（如仅放营业执照、空白签章页、报价空表）仍须创建占位文件。
- 文件命名：两位序号前缀（`01-投标函.md`、`03-第2章第1节-系统架构设计.md`、`09-开标一览表.md`）；序号连续唯一，文件名章/节编号与文内标题一致。

### 4.4 占位内容（每章/节文件至少含）

标题（与招标一致）、占位说明（待撰写/待附扫描件）、招标条款摘要（+甲方诉求，知识库模式）、来源依据区、待确认项区。

**占位文件未创建完成前，不得开始 P6 正文。**

## P6：正文撰写

> 来源：technical-solution-writing 阶段 5 + tender-writing 阶段 D + 甲乙知识库版阶段 D

### 6.0 字数设置门禁（新增：正式动笔前必做）

进入任何正文撰写前，**必须先向用户确认字数目标（以万字为单位）**：

1. **提问口径**：向用户确认本次投标文件的总字数目标（万为单位）。默认按技术响应文件设置主字数（如「技术标 3 万字」）；商务/报价部分如用户未单独指定，按招标范本自然篇幅执行，不强制凑字。
2. **可分层设置**：允许用户分别指定「技术标 X 万字」「商务标 Y 万字」「报价标 Z 万字」，或只给一个总字数由本技能按评分权重拆分。
3. **拆分规则**：技术标总字数按 P4 节结构与评分权重分配到各节，维护「节-评分点-权重-目标字数-完成字数」跟踪表。
4. **字数口径**：纯文本字数（不含占位符、说明性文字、代码、图片标注）；误差 ±5%，宁愿多不要少；字数统计仅用于撰写管控，**不写入正式文件**。
5. **门禁**：未确认字数目标前，不得开始撰写正文。用户要求「精简版」或有页数上限时，先按约束重新分配字数预算：优先压缩低权重节，保留高权重节论证深度与量化指标。

### 6.0.1 图表规划前置门禁（与字数门禁并列，正式动笔前必做）

进入正文撰写前，在确认字数的同时，**必须先产出「图表规划表」**（逐节预判配图类型并记录理由，写入 `写作任务单.md` 的配图列），未产出不得动笔：

1. **规划动作**：按 P4 节结构逐节判断该节命中「数据 / 对比 / 趋势 / 占比 / 构成 / 排名 / 数量」还是「流程 / 因果 / 层次 / 循环 / 状态 / 结构 / 时序 / 职责 / 依赖」，预判配图类型（kami 数据图 / 结构流程图 / 不配图），并记录理由。
2. **判断标准**：命中「图比文字更清楚」且能表达层次 / 方向 / 数量三类信号之一才配图；两项对比用表格、一句话能说清则不配。约每 2000 字 1 图，技术标每章至少 1 图。
3. **不编造数据**：数据类图表仅在有真实数据时绘制；无数据一律写 `【待用户提供：XX数据】` 并列入待补清单，不得为配图编造数字。
4. **门禁**：未产出图表规划表（写作任务单含配图列）前，不得开始撰写任何正文；每节写完须回看 6.9 决策树核对配图是否落实，并在终检（P10）执行图表覆盖检查。

> 本条为强制前置门禁，与 6.0 字数门禁并列：**动笔 = 已确认字数 + 已产出图表规划表**，二者缺一不可。

### 6.1 撰写顺序与前置核对

- 按 P3 选定范围顺序撰写（先商务后技术后报价，或按招标顺序）；一次只聚焦一个单元（章或节），完成闭环不跨多节泛写。
- **写每一章/节前必须**：① 回看招标文件原文对应条款；② 读甲方知识库相关思路/规范（知识库模式）；③ 读乙方知识库相关案例/方案/资质（知识库模式）。三步完成后才落笔。
- 商务文件严格照搬招标格式范本：结构/措辞照搬，只填空不扩写，缺信息写 `【待用户补充：xxx】`。
- 商务/技术/报价分册时分别撰写，交叉引用用简短说明指向另一册（如「详见技术文件第 3 章《核心技术方案》」）。
- 角色与语气：以投标方（乙方）口吻撰写；甲方称呼用招标方官方名称，乙方称呼用乙方单位名称；正文不得出现「根据甲方知识库/乙方知识库」等过程性字样。

### 6.2 技术正文篇幅与深度硬约束（防缩水）

- 普通节正文建议 ≥ **900 字**；关键节（高风险/高复杂度/评分高权重）建议 ≥ **1500 字**；如 P6.0 已设万字目标，则以拆分后的节目标字数优先。
- 每节至少覆盖 **7 要素**：节目标与范围、现状与问题、方案设计与技术路线、关键参数与配置建议、实施步骤与里程碑、风险与应对、验收标准与交付物。
- 每节至少包含：**1 张参数/能力对照表 + 1 组实施步骤清单（≥6 步）+ 3 条可核查量化指标**。
- 每个单元按「目标 → 设计 → 落地 → 验收」展开，末尾给出关键决策、依赖条件、待确认事项。
- 输出前执行防缩水自检：字数、7 要素、表格、步骤清单、量化指标任一缺失先补齐再交付。

### 6.3 按评分权重分配篇幅

- 有评分细则时，按评分权重分配各节目标字数；无明确分值按关键性与复杂度估算并标注为估算。
- 公式：`节目标字数 = 技术正文总目标字数 × (该节权重 / 技术节总权重)`，按 50 或 100 字取整。
- 高权重节字数与证据密度不得低于低权重节；否则优先补高权重节。

### 6.4 技术标内容深化（知识库模式必做，其余建议）

- 标题/要点须逻辑化阐述（背景→方案→优势→落地保障），不得仅罗列框架；内容完整、语言通顺、逻辑闭环，贴合甲方诉求与乙方同类案例。
- 图文并茂：技术方案用流程图/架构图（Mermaid）、数据类柱状/折线（kami 数据图）、对比类表格；约每 2000 字配 1 张，技术标每章至少 1 张；图表标注清晰标题、数据源、单位。**图表自动判断与生成规则见 6.9**。
- 图片嵌入优先级：乙方知识库/图片库（`c:/knowledge`）→ 网络（下载存 `images/`）。图片命名 `{章节名}-{图片类型}-{序号}.png/jpg`；注意区分知识库绝对路径（`c:\knowledge\images`）与工作区相对路径（`images/`）。
- 师资填充：从乙方知识库/图片库提取，按招标类型匹配，每种类型**超额 2 位**、按资质等级/经验排序；**逐个师资介绍（不用表格）**；提取该师资**全部**资质图片、不得遗漏、不得张冠李戴、不得重复；无合适师资保留占位并标注。师资资质图片排版每行 2 张、高度一致；非师资图片每行 1 张居中。
- 正式文件净化：移除「字数统计/累计字数/完成率」「招标条款摘要」「图片来源说明」「字数目标」「待撰写/待附扫描件」等说明性文字，仅保留正式投标内容。

### 6.5 报价响应文件撰写规则

- 严格按招标报价格式（开标一览表、分项报价表、投标函报价）填写，**金额、计价方式、税率、最高限价均不得编造**。
- 报价数据未提供时写 `【待用户提供报价】` 占位，并列入待补清单；不得自行估算金额或虚构分项。
- 报价与商务/技术正文中的金额、工期、数量引用保持**一致**（如技术方案提到的规模数字与分项报价表对得上）。

### 6.6 证据与可追溯

- 招标场景：每次写作前回看招标原文对应条款再落笔，关键结论标注来源（「依据招标文件第 X 章第 Y 条」）。
- 需求驱动场景（无招标文件）：关键结论标注依据类型（用户输入/通用实践/工程假设）。
- 禁止仅凭记忆或仅依据摘要二次转写；条款冲突或不清晰时先停下向用户确认。

### 6.7 表达要求

专业、客观、可执行，避免营销化空话；优先量化指标；无法量化时说明测算方法与前提。以「读感像有经验的技术人员写的方案」为第一标准，字数为第二标准。

### 6.8 检查图片嵌入（写完即查）

完成所有章节后检查图表嵌入状态：正常 → 提示可进入后续核验；异常 → 列出异常章节与原因，问是否进入图片补全。图片补全规则同 6.4（师资图片只从知识库/图片库提取，无则不联网、留占位；其他图片可网络补充，下载转 jpg/png 存 `images/` 后按相对路径嵌入）。

### 6.9 图表自动规划与生成（写正文时自动判断，融入 kami 数据图 + Mermaid）

> 本小节为新增能力：正文撰写阶段即**自动判断是否需配图并就地生成**，而非等到 P8 才补图。P8 只负责统一校验/规范化已生成图表。

**一、自动判断（先问「图是否比文字更清楚」）**

写每一节时，对下列内容**主动判断**是否需要配图；判断标准：图能表达「层次/方向/数量」三种信号之一、且比纯文字更清楚时才画；纯对比两项用表格、一句话能说清用句子，**不强行配图**。

- 命中「数据、对比、趋势、占比、构成、排名、数量」→ 生成**数据图表**（kami SVG，见「二」）。
- 命中「流程、因果、逻辑、层次、循环、状态、结构、时序、职责、依赖」→ 生成**结构/流程图**（kami SVG 或 Mermaid，分工见「二」「三」）。
- 约每 2000 字配 1 张图；技术标每章至少 1 张；关键节（高权重/高复杂度）至少 1 张结构图 + 1 张数据图。

**二、kami SVG 图表（14 种内联原语 + 自动选型决策树）**

kami 的 SVG 图表是**内联原语**（非独立文档），存放在 `assets/diagrams/`，统一走羊皮纸底 `#f5f4ed` + 墨蓝强调 `#1B365D` + 衬线标签体系，靠 `references/diagrams.md` 的选择指南与 token 映射驱动抽取 `<svg>` 嵌入长文档 `<figure>`。**共 14 种**：

**结构/关系类（7 种）**

| 图表 | 适用语义 | 模板 |
|---|---|---|
| Architecture 架构图 | 系统组件 + 连接关系（单图有节点预算；五层全景用 `architecture-board`） | `architecture` |
| Flowchart 流程图 | 决策分支、条件流转（菱形判断 + 矩形处理） | `flowchart` |
| Tree 树状图 | 深度 ≥2 的层级（组织架构 / 分类树） | `tree` |
| Layer Stack 分层图 | 垂直堆叠的系统分层（OSI / 前端分层架构） | `layer-stack` |
| Venn 维恩图 | 2–3 集合的交集与重叠属性 | `venn` |
| Swimlane 泳道图 | ≥3 角色/团队横向职责流 | `swimlane` |
| State Machine 状态机 | 有限状态 + 有向转移（生命周期 / 订单态流转） | `state-machine` |

**战略/时间类（2 种）**

| 图表 | 适用语义 | 模板 |
|---|---|---|
| Quadrant 象限图 | 2×2 定位矩阵（优先级 / BCG / 能力×意愿） | `quadrant` |
| Timeline 时间线 | 时间轴 + 里程碑 / roadmap 节点 | `timeline` |

**统计/数据类（5 种）**

| 图表 | 适用语义 | 模板 |
|---|---|---|
| Bar Chart 柱状图 | 分类对比，≤8 组×3 系列；同快照多系列用 Grouped Bar | `bar-chart` |
| Line Chart 折线图 | 时间序列趋势，≤12 点×3 线 | `line-chart` |
| Donut Chart 环形图 | 单系列占比 ≤6 段（≥7 段改横向条形） | `donut-chart` |
| Candlestick K线图 | OHLC 股价/商品日行情，≤30 天 | `candlestick` |
| Waterfall 瀑布图 | 收入桥 / P&L 分解、正负贡献累加到总数 | `waterfall` |

**自动选型决策树（首匹配胜出，Agent 直接套用）**

1. 有 open/high/low/close → **Candlestick**
2. 正负贡献累加到一个总数 → **Waterfall**
3. 单系列占比 ≈100% 且 ≤6 项 → **Donut**（≥7 项改 **Horizontal Bar**）
4. 多系列跨时间 → **Line**；单系列跨时间且看绝对量变化 → **Bar**
5. 同快照多系列分类 → **Grouped Bar**
6. 2×2 战略定位 → **Quadrant**
7. 层级深度 ≥2 → **Tree**；决策分支 → **Flowchart**
8. ≥3 角色跨团队 → **Swimlane**；2–3 集合交集 → **Venn**
9. 其余单系列分类无时间轴 → **Bar**

**使用约束（防 AI-slop，必守）**

- 画图前先问：**「一段写得好的文字会不会比这张图教得更少？」**——否就不画。
- 所有图表必须嵌在 `<figure>` 里，`<figcaption>` 写**洞察**（如「Q3 收入环比 +18%，主要由华东区拉动」）而非数据范围。
- 不引入外部 JS 图表库，**纯手写 SVG**，跟随 tokens.json 的墨蓝 `#1B365D` / 羊皮纸 `#f5f4ed`，**无渐变、无阴影、无 3D**。
- 数值类内容可不经追问直接选图嵌入；但**架构图超节点预算（>9 节点）时必须先写结构大纲再渲染**。
- 不编造数据：无数据写 `【待用户提供：XX数据】` 并列入待补清单；标注数据源与单位；坐标/宽度取 4 的倍数；焦点 1–2 个墨蓝强调、其余暖灰。

**三、Mermaid 互补（图源码路径：流程/时序/甘特/状态/类图）**

kami SVG 是「印刷成品图」，一经渲染即定稿、不易再改；当需要**可编辑图源码、快速迭代、或 P8 语法级校验**时，用 Mermaid 就地写 ` ```mermaid ` 代码块。二者分工：

- **印刷交付、审美优先 → kami SVG**（上述 14 种，嵌入 Word/PDF 与正文完全同肤）。
- **可编辑 / 可校验 / 快速迭代 → Mermaid**：流程、时序、甘特、状态、类/实体等「图源码」，渲染时可经 kami 的 beautiful-mermaid 管线转成 kami 风格图（羊皮纸 + 墨蓝），或直接 mermaid 渲染。

| 内容语义 | Mermaid 类型 |
|---|---|
| 分层架构 / 模块关系 / 组织结构 | `flowchart TB` + `subgraph` |
| 业务流程 / 决策分支 / 因果链 | `flowchart LR` 或 `flowchart TD` |
| 系统交互 / 接口调用顺序 | `sequenceDiagram` |
| 实施计划 / 里程碑 / 工期 | `gantt` |
| 生命周期 / 状态流转（循环/状态机） | `stateDiagram-v2` |
| 类/实体关系 / 数据模型 | `classDiagram` 或 `erDiagram` |
| 泳道式多角色协同 | `flowchart` + `subgraph`（按泳道分组） |

Mermaid 规矩：节点 ID 含中文/空格/符号用双引号；`subgraph`/`end` 成对；箭头语法合法；语义不适合用图则标「保留文字」；生成后标注「本图待 P8 校验」。

**四、图表标注规范**

每张图配**图题**（图 N-x 标题）+ 必要**数据源/单位**，字体用图表标注档（9pt，衬线）；图是正文补充而非唯一载体，不删正文文字说明。

**五、与 P8 的关系**

P6 生成图表后不即时校验语法；**P8 统一校验/转换/规范化**所有 Mermaid 与数据图（含 Mermaid 语法实跑、ASCII 伪图转 Mermaid、数据图规范核查），P8 仍为可选后处理但**建议定稿前执行**。若用户跳过 P8，终检（P10）须额外检查图表语法是否可渲染。

## P7：技术标润色与去 AI 化（可选后处理）

> 来源：tender-technical-refine

### 7.0 首要目标

**第一优先级不是堆字数，而是把正文主体改写为自然语言连贯段落并去 AI 化。** 成稿应读起来像有经验的技术人员撰写的方案说明，而非模型生成的提纲填空或宣传稿。

- **自然语言正文**：以段落为主，有主线（背景/问题 → 思路做法 → 参数步骤效果），可朗读，避免空洞形容词堆砌。
- **去 AI 化**：主动清除空泛承诺（「本项目将…」「全方位/一体化」无后续具体动作）、提纲体、机械连接词（首先/其次/最后、滥用「综上所述」）、重复句式、假大空、列表代替论证。
- **去 AI 化 ≠ 删技术内容**：参数表、步骤清单、条款响应、数字指标保留，改的是写法。

### 7.1 处理规则

1. **忽略助手感知与 UI 状态**：不得以当前打开文件/光标/最近编辑决定处理范围；唯一依据是**扫描工作区技术目录 `.md`**，按目录/文件名顺序逐文件处理。开场直接列扫描清单并从首节开始。
2. 处理范围：技术卷各节 `.md`（含章级索引页可略改说明性文字）；**排除**商务卷、报价卷、格式范本「仅填空」章节、证据图、用户标注「定稿勿动」的文件。
3. 步骤 A（去 AI + 自然语言，必做）：能段落化的改写为段落；合并意义重复的小标题；删除/改写空泛套话；段首避免连续同模板；顶部 HTML 注释/评分点说明/占位可保留。
4. 步骤 B（加厚，按需）：叙述达标后再补机理、场景、对比、实施细节、风险；用户指定字数优先，无指定时 900/1500 字仅作参考，**不得为达标恢复 AI 套话**。
5. 步骤 C（落盘自检）：保持文件名/节编号/标题层级；自检正文是否自然段落、是否去 AI、锚点是否仍在、有无未证实事实。
6. 用户明确约束（只改某节、勿动商务卷、简版）必须遵守；占位为主无可写实质的节可跳过并说明。

**严格禁止**：❌ 分析 UI 状态；❌ 输出仍以 bullet 为主几乎没有段落；❌ 用「本项目将高度重视…」灌水；❌ 改商务范本或编造资质/报价数据；❌ 为扩写删除参数表/指标/步骤/条款响应；❌ 无用户同意大规模重排目录。

## P8：图表校验与规范化（可选后处理，Mermaid + 数据图）

> 来源：tender-technical-mermaid。**与 P6.9 的关系**：P6.9 在正文撰写时自动判断并就地生成图表（数据图用 kami SVG、流程/结构图用 Mermaid），本阶段负责统一校验、转换、规范化这些已生成图表；若图表由他处而来或用户跳过 P6.9，本阶段同样兜底补图建议。

### 8.1 处理模式（必须先确认）

| 模式 | 行为 | 是否写回 md |
|------|------|-------------|
| 仅校验 | 扫描+校验 Mermaid/数据图，输出问题清单 | ❌ |
| 校验+建议（默认） | 加列建议转换项与草案 | ❌（直至用户确认） |
| 校验+改写 | 仅对已确认项执行转换并再次校验 | ✅ |

用户未表态默认「校验+建议」，禁止直接改文件。

### 8.2 处理范围

纳入：目标目录全部 `.md`（节级+索引页）；已有 ` ```mermaid ` 块；kami 数据图（内联 SVG 的柱状/折线/环形等）是否规范；非 mermaid fenced code 画的关系型图示；正文用 `│`/`──`/`└─` 画的架构/流程伪图。

排除：`![...](...)` 扫描件/证照/截图/彩页（证据图）；商务文件、报价文件；纯参数表/符合性矩阵/报价表（勿强行改图）；用户标注「定稿勿动」。

### 8.3 执行

1. 扫描并记入 `技术文件/图表处理清单.md`（文件/位置/类型/语义/建议动作）。
2. Mermaid 校验：围栏正确、图表类型匹配、节点 ID 含中文/空格/符号时用双引号、`subgraph/end` 成对、箭头语法合法；优先实跑验证，否则静态规则 + 通读标注疑似错误与修复建议；汇总 `图表校验报告.md`。
3. 转换建议：保留原意不臆造节点；Mermaid 类型映射见 6.9 第三段——分层架构→`flowchart TB`+`subgraph`、业务流程/决策/因果→`flowchart LR/TD`、系统交互/接口时序→`sequenceDiagram`、实施计划/里程碑→`gantt`、生命周期/状态流转→`stateDiagram-v2`、类/实体关系→`classDiagram`/`erDiagram`、多角色协同→泳道式 `flowchart`；kami SVG 图按 6.9 第二段的 **14 种全量 + 自动选型决策树**执行（数据/结构/时间/战略类均可用）；语义不适合用图则标「保留」。
4. 写回：仅用户确认后，一次处理一个文件或指定批次；替换对应区间、不改变前后编号标题、禁止删证据图、版式显著变化时顶部加 `<!-- 图表已由 ASCII 转为 mermaid，日期 -->`。
5. 复检：对已改文件重跑校验，更新清单/报告，汇报校验数量与未改项。

## P9：定稿清理（可选后处理）

> 来源：tender-technical-finalize

### 9.1 处理模式（必须先确认）

| 模式 | 行为 | 是否写回 md |
|------|------|-------------|
| 仅扫描 | 列拟清理项与残留占位 | ❌ |
| 扫描+清单（默认） | 写 `技术文件/定稿清理清单.md`，待用户确认 | ❌ |
| 确认后清理 | 按确认的文件/规则删元数据 | ✅ |

用户未表态默认「扫描+清单」，禁止直接改正文。

### 9.2 何谓「写作元数据」（应剥离）

- **A 节首连续 blockquote 元信息块**（评分点/招标文件来源/附件状态/强约束/写作提示等）→ 可删；招标条款原文摘录保留；删除后孤立 `---` 一并删。
- **B 顶部 HTML 注释** `<!-- ... -->`（写作备注/条款映射/字数跟踪）→ 删。
- **C 用户占位** `【待用户补充：xxx】` 等：仅用户确认已补全后删；未确认一律保留并写入「残留占位清单」。
- **D 文末写作尾巴章节**（整节删）：`字数与评分点对应`、`否决项自检`、`附件清单（占位）`。
- **E 正文中的写作向 blockquote**（评分点 T-x 关注/当前状态缺失/内部演算口吻）→ 删或去 `>`；招标条款摘录保留。
- **F 表格写作痕迹**：`评分要求/是否满足` 列删「是否满足」、改「评分要求」为「招标要求」；技术参数行不删。
- **G 章级索引与编制说明**：删写作跟踪列/编制原则/否决项自检；默认索引类文件移 `中间件/`。
- **H 必须保留**：正文自然语言段落、参数表、符合性矩阵、实施步骤表、技术数据、正文正式引用、证据图、报价表格。

### 9.3 中间件不混删

`标书解析.md`、`漏项清单.md`、`写作任务单.md`、`解析总表.md`、`图表处理清单.md`、`润色进度.md`、`定稿清理清单.md` 属过程件，默认不改正文；由用户选择保留原位或移 `中间件/`，禁止为图省事直接删除。

### 9.4 执行与自检

扫描逐文件检测元数据类型并写清单；用户确认后逐文件删除元数据，**不改标题编号体系、不润色、不改技术观点与数字**；清理后自检——无残留评分点类块、无文末三章、无未确认占位被误删、证据图路径仍在、无标题下空白断层、索引已移中间件或去写作列。

## P10：终检与合规审查（交付前必做硬门禁）

> 来源：tender-writing 阶段 F + tender-bid-review。自写标书跑「终检」，审查他人/已有标书跑「合规审查」，共用一份报告框架。

### 10.1 双轨对照原则（终检核心）

1. **原文对照轨（主轨）**：必须**重新打开并检索招标文件原文**逐条对照。**禁止**仅凭中间件/对话记忆做终检。
2. **解析对照轨（辅轨）**：将实际产出与阶段 P2 中间件逐条勾对；冲突时**以原文轨为准**，并回写修正中间件。

### 10.2 审查执行（合规审查）

1. **先读投标文件锁定目标包**（投标函/开标一览表/封面目录/报价清单/正文反复出现项），产出「投标侧锁定记录」；投标无包号但内容对应某包 → 标记「疑似第 X 包」须向用户确认；投标声明包与招标包列表对不上 → 阻塞写入报告。
2. **再读招标文件定位该包条款**（仅展开本包相关区间，其它包标记 N/A），产出「招标侧锁定记录」，验证一致。
3. 从招标原文生成审查清单：投标文件组成、否决/废标项（逐条）、评分点、格式与递交、技术实质性、报价要求、条件性条款（逐条判适用/不适用）。
4. 映射投标结构（✅ 有实质 / ⚠️ 仅占位 / ❌ 缺失）。
5. 符合性与否决项逐条审查，否决项专表单独汇总。
6. 评分覆盖审查，产出评分覆盖表。
7. 格式、商务范本、技术实质性、报价一致性、附件占位审查（不替代人眼验真证照签章）。
8. 一致性与交叉引用反查（跨包混用为高否决风险；报价金额跨章节一致性）。

### 10.3 终检清单（F1–F5）

- **F1 文件存在性**：列出实际 `.md` 清单，与阶段 P2 对照表逐条比对 ✅/⚠️/❌；声称已建但工作区不存在 → ❌。**注意核对 P3 选定范围**：未选中部分不列入缺失。
- **F2 原文全量对照**：按「投标文件组成/报价文件/符合性否决项/评分点/技术实质性/交叉引用脚注/递交形式」维度逐条建立对照表，条件性条款逐条判适用/不适用。
- **F3 中间件闭环**：`漏项清单.md` 每条须有终态（✅已补/⏳待用户/➖不适用+依据）；统计占位与未插图数量。
- **F4 差异处理**：原文有而解析无 → 写入漏项清单标「终检新发现」→ 补建/补写 → 重新跑 F1–F3。
- **F5 产出报告**：`终检报告.md`（或 `审查报告.md`），含摘要、原文对照主表、解析对照辅表、差异说明、用户待补清单、结论（✅通过/❌未通过）。

### 10.4 交付门禁（全部满足方可宣称完成）

- 原文对照表中所有必填条目为 ✅ 或 ➖（不适用且注明依据），无 ❌。
- 所有否决/废标风险条目已响应或已明确待用户补件且不构成立即否决（报告中说明）。
- 工作区文件清单与对照表一致，无「声称已建但无文件」。
- `漏项清单.md` 无未处理开放项。
- 报告已写入工作区且结论为 ✅。
- `废标项检查报告.pdf` 已在标书同目录生成，且结论为 ✅ 或 ⚠️（无 ❌）（见 10.5）。

**严格禁止**：❌ 仅对照中间件不回读原文；❌ 凭解析结论推断成稿完整不做原文二次检索；❌ 只查有无 md 不打开原文核对范本子项与脚注；❌ 发现漏项只口头说明不写报告不补文件；❌ 未授权修改投标正文；❌ 用其它包要求审查本包；❌ 将占位判为已满足；❌ 宣称替代法务/合规/签章密封人工终审；❌ 对扫描件/证照做真伪鉴定。

### 10.5 废标项全面检查与报告（新增：废标项专项门禁）

> 来源：网络检索 + 《招标投标法实施条例》第 51 条。终检时对废标/否决项做**双重排查 + 逐项对应 + 独立报告**，确保零废标风险遗漏。

**一、双重排查（法定 7 种 + 12 大类）**

1. **法定否决情形（必查 7 种，逐条核对）**——依据《招标投标法实施条例》第五十一条，评标委员会应当否决其投标的情形：
   - V1 投标文件未经投标单位盖章和单位负责人签字；
   - V2 投标联合体没有提交共同投标协议；
   - V3 投标人不符合国家或招标文件规定的资格条件；
   - V4 同一投标人提交两个以上不同投标文件或投标报价（招标文件要求备选投标的除外）；
   - V5 投标报价低于成本或高于招标文件设定的最高投标限价；
   - V6 投标文件未对招标文件的实质性要求和条件作出响应；
   - V7 投标人有串通投标、弄虚作假、行贿等违法行为。
2. **实务分类排查（12 大类，逐类过筛）**：按 P2.3 的「废标项分类框架（12 大类）」逐类核对，补齐招标文件明示否决条款之外的隐性废标风险（资质、业绩、报价、格式、签章、密封、时限、技术/商务实质偏离、保证金、串标造假、其他）。

**二、输出文件与废标项一一对应检查（新增核心）**

对每一个废标/否决项，**必须定位到输出投标文件的具体位置**，建立一一对应，不得笼统写「已响应」：

| 字段 | 说明 |
|---|---|
| 废标项编号 | V-xxx（法定）或 B-xxx（分类） |
| 废标条件 | 招标依据条款 + 触发条件摘要 |
| 对应输出文件 | 如 `商务文件/02-资格证明.md` 第 X 项、`报价文件/09-开标一览表.md` 金额栏 |
| 检查结果 | ✅ 已覆盖 / ⚠️ 风险（待补/待确认）/ ❌ 缺失 |
| 风险等级 | 高（直接否决）/ 中（可能否决）/ 低（格式瑕疵） |
| 补救动作 | 补件 / 修改 / 待用户确认 |

**三、废标项检查报告（独立 PDF，必交付）**

在**标书输出同目录**（`投标文件/` 或用户指定根名）输出独立报告：

1. 先产出 `废标项检查报告.md`，再转 **`废标项检查报告.pdf`**（PDF 为必交付格式）。
2. 报告内容结构：
   - **一、检查范围与方法**（法定 7 种 + 12 大类框架 + 一一对应检查法）；
   - **二、法定否决情形核对表**（V1–V7，每项 → 是否触发 → 对应输出文件位置 → 检查结果）；
   - **三、废标项逐项检查表**（全部废标项：编号/类别/招标依据/废标条件/对应输出文件/检查结果/风险等级/补救动作）；
   - **四、输出文件与废标项对应关系**（反向索引：每个输出文件 → 命中了哪些废标项，确认无文件遗漏废标项）；
   - **五、未响应与待补清单**（⚠️/❌ 项集中列出，含用户需补件清单）；
   - **六、结论**（✅ 无废标风险 / ⚠️ 有风险待补 / ❌ 存在废标项，须修复后再交付）。
3. PDF 排版沿用 P11 排版审美规范（墨蓝表头、表格边框与对齐规则见 11.6），表格字段与上文一致。

**四、门禁（纳入 10.4）**

未通过本检查（报告结论为 ❌）或 `废标项检查报告.pdf` 未生成于标书同目录，**不得宣称交付完成**。

## P11：输出格式确认与交付（Word / PDF，应用排版审美）

> 来源：甲乙知识库版阶段 G + 选择性融入 kami

### 11.0 输出格式确认（新增：导出前必问）

交付导出前，**必须向用户确认输出格式**：

1. **提问口径**：本次交付需要哪些格式？① Word（.docx，可编辑）② PDF（版式锁定）③ 两者都要。用户未表态默认「两者都要」，但须先确认再导出。
2. 同时确认交付范围：是否包含商务/技术/报价全部（与 P3 一致）、是否拆分册、是否需封面/目录页。
3. **门禁**：未确认输出格式前，不得开始合并/导出；导出完成后须汇报每种格式的文件路径与是否成功。

### 11.1 合并

1. 按顺序将选定范围内各章 `.md` 合并（技术标合并为 `技术文件合并.md`；如需分册，商务/技术/报价各合并一册）。
2. 合并前确认已完成 P9 定稿清理（如有）与 P10 终检通过。

### 11.2 Word 输出

1. 将合并 `.md` 转换为 `.docx`，**图片必须打包嵌入**，相对路径不失效。
2. 转换失败告知原因；成功告知已完成并给出路径。
3. 应用「排版审美规范」（见下节）中的字体/字号/间距/留白设置，按「Word 落地映射」逐项落地 kami 令牌；Word 版优先保证**可编辑 + 层级清晰 + 表格规范**，并**如实告知 Word 审美上限低于 PDF**（见「融入边界」诚实声明）。
4. **表格格式（硬性）**：所有表格必须应用「表格格式规范」（见 11.6）——边框可见、表头有样式、长表跨页重复表头；**禁止交付无边框/无表头的裸表**。
5. **字体默认嵌入（硬性）**：使用内置字体 `assets/fonts/`（见「本地字体资产」）。导出前将仓耳今楷 02 / 思源宋体安装到系统，并**默认执行字体嵌入**（见 11.5 字体嵌入规范），确保文件在其他电脑打开不丢字体、不被替换为默认字体；不便安装商业字体时回退到思源宋体 SC。

### 11.3 PDF 输出（审美优先，必须走 kami HTML 渲染管线）

> **为什么 PDF 不如 kami 直接输出好看？** 根因在于「Word 流式排版 + pandoc 朴素路径」复现不了 kami 的 CSS 级审美（字距、百分比行高、背景色块、留白栅格、轻阴影）。**PDF 要追平 kami 审美，唯一路径是复用 kami 的 HTML + CSS 排版管线**，而非从 Word 转 PDF。

1. **首选路径（kami HTML 渲染，必用）**：将合并 `.md` 转成 **kami 风格 HTML**——复用 kami `long-doc.html` 模板结构与 `references/tokens.json` 设计令牌（暖羊皮纸底 `#f5f4ed`、墨蓝 `#1B365D` 单强调色、衬线层级、行高/字距/留白栅格、表格/图表样式），经 `@font-face` 引用 `assets/fonts/` 本地字体，用 WeasyPrint / Chromium 渲染 PDF。
2. **次选路径（Word 转 PDF）**：仅在用户明确只要「由 Word 导出 PDF」时使用；须核对分页、字体嵌入、图表不截断，并**如实告知审美低于 HTML 渲染路径**。
3. **字体默认嵌入（硬性）**：HTML 渲染经 `@font-face` 引用 `assets/fonts/` 本地字体，WeasyPrint / Chromium **默认嵌入字体子集**；Word 导出 PDF 勾选「嵌入字体」。**不得交付未嵌入字体的 PDF**（见 11.5）。
4. **审美自检（交付前，必做）**：PDF 须同时满足——暖羊皮纸底（非纯白）、墨蓝单强调色、标题衬线不加粗靠字号留白分层、行高/字距/留白栅格生效、表格带墨蓝表头与可见边框、图表扁平单线几何。任一不达标即回炉重排，不得宣称「已应用 kami 审美」。
5. 交付前建议**人工通读一章**；本技能不替代法务/合规终审。

### 11.4 交付完成标准（Definition of done）

向用户交付时，须在收尾消息中说明：

1. 每种承诺格式的**文件路径**；
2. 已执行的校验及结果（含终检结论、图表校验、字数达标情况、**字体嵌入状态**）；
3. 仍存在的 `【待用户补充】` 缺口清单（若有）；
4. 排版视觉结论（PDF 是否走 kami HTML 渲染管线、是否经视觉校验；未能可视化检查时如实说明「构建已验证，视觉未确认」，不得宣称已完美排版；Word 是否已按「Word 落地映射」应用样式并说明其审美上限）；
5. **字体嵌入确认**：所用字体均已嵌入（或明确说明哪一字体回退及原因），不得交付未嵌入字体的文件。

### 11.5 字体嵌入规范（默认执行，防跨机丢字体）

**目标**：交付的 Word/PDF 必须自带字体信息，在其他电脑打开不依赖本机字体、不被替换为默认字体、不出现缺字方框。

#### Word（.docx）

默认执行字体嵌入，两种落地方式（优先方式一）：

- **方式一（自动化，推荐）**：用 Word COM 自动化（Windows PowerShell / VBA）设置并重存：
  ```powershell
  $word = New-Object -ComObject Word.Application
  $word.Visible = $false
  $doc = $word.Documents.Open("$PWD\技术文件合并.docx")
  $doc.EmbedTrueTypeFonts = $true          # 嵌入 TrueType 字体
  $doc.SaveAs2("$PWD\技术文件合并.docx", 16)  # 16 = wdFormatXMLDocument（docx）
  $doc.Close()
  $word.Quit()
  ```
- **方式二（手动）**：Word 打开文档 → 文件 → 选项 → 保存 → 勾选「将字体嵌入文件」，并建议勾选「仅嵌入文档中使用的字符」「不嵌入常用系统字体」（减小体积）。

注意：

- 嵌入字体后文件体积增大（中文衬线字体子集仍较大）属正常；不嵌入则跨机丢字体的代价更高。
- 商业字体（仓耳今楷 02）能否嵌入由 Word 依据字体许可位（fsType）决定；若 Word 拒绝嵌入该字体，**回退到思源宋体 SC**（OFL 开源、允许嵌入）并保持衬线审美。
- pandoc / python-docx 生成的 docx **不直接支持字体嵌入**，须经上述 Word COM 或 Word 手动「嵌入字体」补齐后再交付。

#### PDF

- **HTML 渲染（WeasyPrint / Chromium）**：`@font-face` 引用的本地字体会**默认嵌入字体子集**，无需额外操作；交付前抽查 PDF 字体表确认字体为嵌入（Embedded / Embedded Subset）。
- **Word 导出 PDF**：Word 导出 PDF 默认嵌入 TrueType 字体；导出时保持「嵌入字体」勾选，导出后抽查分页与字体。

#### 交付前字体校验（必做）

1. **Word**：打开「文件 → 信息 → 属性 → 高级属性 → 字体」，确认所用字体状态为「完全嵌入 / 子集嵌入」，而非「未嵌入」。
2. **PDF**：用 PDF 阅读器查看「文档属性 → 字体」，确认仓耳今楷 / 思源宋体 / Charter 等显示为 Embedded / Embedded Subset。
3. 若任一字体无法嵌入，向用户说明原因并给出替代（回退思源宋体 SC），不得静默交付未嵌入字体的文件。

### 11.6 表格格式规范（Word/PDF 交付必做）

> 本规范解决「Word 表格无边框、表头无样式」问题，P11 导出时**必须应用**，未应用不得交付。

**表格边框（硬性）**

- 所有交付表格必须有**可见边框**：外框用墨蓝/暖灰实线，内线（行分隔）用浅暖灰实线；**禁止无边框表格**（`.md` 转 `.docx` 后默认网格边框消失是常见事故，必须回补）。
- 参数表/符合性矩阵/报价表等**正式内容表**必须带完整网格线（外框 + 行线 + 列线）；纯排版的说明性列表可用「表头下边框 + 行分隔线」的轻量样式，但**表头与正文之间必须有分隔线**。

**表头样式（硬性）**

- 表头行**底色墨蓝 `#1B365D`、文字暖白 `#faf9f5`**（Word 对应：深蓝底 + 白字），表头文字用衬线常规字重（500），**不依赖加粗**；备选（范本不允许底色时）：表头无底纹但加墨蓝**下边框**（0.75–1pt）+ 深色表头文字。
- 表头文字对齐（硬性）：**上下左右居中**（水平居中 + 垂直居中）。
- 表头在跨页时**重复显示**（Word「表格属性 → 行 → 允许跨页断行 + 在各页顶端以标题行形式重复出现」）。

**单元格排版**

- 单元格内文字用「密集正文/表格」档 9.5pt、行高 1.42，内边距上下 2–3pt、左右 4–5pt。
- **单元格对齐规则（硬性）**：
  - 表头行（第一行）：**上下左右居中**；
  - 第一列（序号/名称/项目等）：**上下左右居中**；
  - 其余单元格：**上下居中**，水平按内容语义——数字右对齐、文本左对齐、状态/短标签居中。
- 数据列统一小数位与单位；单位标注在表头或表题，不在每个单元格重复。
- 表格与上下文之间留 `lg`（16–20pt）间距；表题用图题/表注档 9pt，居中或左对齐统一。

**实现方式（按导出工具选择）**

- **python-docx（推荐）**：用 `style='Table Grid'` 保证网格边框，再逐表设置表头底纹（`w:shd` 墨蓝填充 + 白字）、行重复表头（`tblHeader`）、单元格边距；**对齐**——表头行与第一列 `cell.vertical_alignment = CENTER` + `paragraph.alignment = CENTER`，其余单元格 `cell.vertical_alignment = CENTER`（水平：数字右对齐、文本左对齐）；写一个统一的表格样式函数复用，禁止逐表手工遗漏。
- **pandoc**：生成 `.docx` 后用 python-docx 或 Word COM 补表格样式（pandoc 默认表格无样式）；或提供 `reference.docx` 定义带边框 + 表头底纹的 `Table` 样式。
- **Word COM**：打开文档后遍历 `doc.Tables`，设置 `Table.Borders.Enable = true`、`Table.Rows(1).Shading.BackgroundPatternColor = RGB(27,54,93)`、表头文字白色，并 `Rows(1).HeadingFormat = true`；对齐用 `Cell.VerticalAlignment = wdCellAlignVerticalCenter`、`Range.ParagraphFormat.Alignment`（表头行/第一列居中，其余数字右对齐、文本左对齐）。
- **HTML→PDF（kami 方式）**：CSS 给 `table` 设 `border-collapse: collapse`、`th` 墨蓝底 + 白字、`th/td` 边框暖灰实线，表头跨页重复由 `thead` 自动处理；对齐用 `th, td:first-child { text-align:center; vertical-align:middle }`、其余 `td { vertical-align:middle }`（数字右对齐、文本左对齐）。

**交付前表格校验（必做）**

1. 逐表检查：边框可见、表头有样式、无「无边框/无表头」的裸表。
2. 抽查长表格跨页时表头是否重复显示。
3. 导出后打开 Word/PDF **实际查看**（不能只信构建日志）；发现裸表立即回补样式再交付。

## 排版审美规范（选择性融入 kami）

> 本规范选择性吸收 kami 排版体系，用于提升投标文件 Word/PDF 输出的排版与审美水平。**适用范围**：技术响应文件正文、封面、目录、摘要页、图表等**自主排版内容**；**不适用**：招标文件格式范本硬性约束的商务章节、签章页、报价表等须按范本执行的部位（范本优先，审美次之）。

### 设计基调

- **暖羊皮纸底**：页面背景用暖白 `#f5f4ed`（或 Word 中近似的米白），**从不用纯白**——纯白在打印件上易显刺眼、廉价。
- **单一强调色**：墨蓝 `#1B365D`，用于标题左栏、表格表头、关键数据强调；**全篇只此一色**，不引入第二强调色。
- **暖灰文字**：所有灰色带黄棕底调，禁用冷蓝灰；标题墨蓝、正文近黑、次级暖灰、三级橄榄灰。
- **衬线标题层级**：中文标题与正文统一用衬线（宋体系），标题不加粗、靠字号与留白分层级，而非靠加粗+多色。

### 十条排版不变量（投标适配版）

1. 页面背景暖羊皮纸 `#f5f4ed`，从不用纯白。
2. 全篇唯一强调色墨蓝 `#1B365D`。
3. 灰色一律暖调（黄棕底调），无冷蓝灰。
4. 每页单一衬线字体（标题+正文同族）；UI 化小标签才可用真实无衬线。
5. 衬线字重锁定常规（500 或 normal），**不依赖加粗**表达层级。
6. 行高：标题 1.1–1.3 / 密集表格 1.4–1.45 / 正文阅读 1.5–1.55。
7. 字距：中文正文 0.1–0.2pt（密集版式可到 0.3pt）；英文正文 0；小标签/全大写眉题 +0.2–1pt。
8. 标签/底色块用**实色**填充，不用 rgba 半透明（Word/WeasyPrint 兼容性）。
9. 深度用「边框/环形 + 轻阴影」表达，不用硬投影。
10. 正式文件正文**不用斜体**。

### 图表审美规范（呼应 P8）

- 图表统一**扁平、单线几何、无渐变、无硬阴影、无 3D**，与正文配色一致（墨蓝主色 + 暖灰辅助）；kami SVG 图表跟随 `tokens.json` 的墨蓝 `#1B365D` / 羊皮纸 `#f5f4ed`，全部嵌入 `<figure>`。
- 图表选型与绘制走 6.9 的「14 种 kami SVG 全量 + 自动选型决策树」；流程图/架构图用 Mermaid 时渲染主题对齐墨蓝 `#1B365D` 单强调色，节点衬线标签，留白充足。
- 图表是正文的补充而非唯一信息载体，不删正文文字说明；`<figcaption>` 写**洞察**而非数据范围。
- 师资资质图片排版：每行 2 张、高度一致、宽度等比；非师资图片每行 1 张居中。

### Word 落地映射（kami token → Word 样式属性）

> Word 是流式排版引擎，复现不了 CSS 的 letter-spacing 字距、百分比行高、背景色块、网格留白、轻阴影等精细效果；本表给出「尽量逼近」的映射，Word 审美上限低于 PDF。

- **页面暖羊皮纸底 `#f5f4ed`**：设页面背景色（`w:background`）或正文段落底纹；Word 打印默认不显示页面背景色时退纯白并向用户说明。
- **墨蓝 `#1B365D` 单强调色**：标题字体色、表头底纹、强调文字色，全篇唯一。
- **衬线标题不加粗**：标题字体用仓耳今楷 02 / 思源宋体，`bold=False`，靠字号 + 段前段后间距分层。
- **正文 10.5pt / 行高 1.55**：段落字号 10.5pt、`line_spacing = 1.55`（或固定行距 ≈ 16.3pt）。
- **字号层级**：按「字号层级」表逐级设 H1 22pt / H2 16pt / H3 13pt / 正文 10.5pt / 表格 9.5pt。
- **间距栅格 4pt**：段前段后间距按栅格映射（节标题上 24–32pt、大节间 40–60pt、章间 80–120pt）。
- **表格墨蓝表头 + 边框**：见 11.6（表头底纹 `#1B365D` + 白字 + 网格边框 + 对齐规则）。
- **图表扁平单线几何**：图表直接用 kami SVG（数据图）或 Mermaid，不在 Word 里重绘。
- **灰色暖调无冷蓝灰**：次级文字 `#3d3d3a`、说明 `#504e49`、三级 `#6b6a64`。

**诚实声明**：Word 因引擎限制无法 1:1 复现 kami CSS 审美（字距微调、背景色块、网格留白、轻阴影均不可靠），交付时须告知用户「Word 为可编辑稿，审美趋近但非最佳；最佳审美请以 PDF（HTML 渲染）为准」。若用户要求 Word 也达到同等审美，明确说明其上限，并询问是否以 PDF 为主交付。

### 融入边界（PDF 复用管线，Word 映射 token）

- **PDF 复用（深度融入）**：PDF 输出**必须复用 kami 的 HTML + CSS 排版管线**——复用 `long-doc.html` 模板结构 + `references/tokens.json` 设计令牌 + `assets/diagrams/` 图表皮肤，经 WeasyPrint/Chromium 渲染。**这是追平 kami 审美的唯一路径，不得再退回 Word/pandoc 朴素路径**（见 11.3）。
- **Word 映射（逼近融入）**：Word 用 python-docx 把 kami 设计令牌逐项映射为样式属性（见「Word 落地映射」），在可编辑性前提下尽量逼近；Word 审美上限低于 PDF，需向用户如实说明。
- **不融入**：kami 的 build.py/checks.py 工程脚本、brand profile 机制、更新检查——本技能自行维护「标书内容 + 排版落地」逻辑，仅复用其**排版资产（HTML 模板 / CSS token / 图表皮肤）与字体**。
- **范本优先**：任何与招标格式范本冲突处，**以招标范本为准**；审美只作用于范本未约束的自由排版区。

- 不编造资质、业绩、参数、预算、报价、测试数据、客户案例、师资信息；缺失用占位并列出待补清单。

## 执行最小清单

1. 先按入口路由判断从哪个阶段切入；再按门禁逐步推进。
2. 投标场景：**P0 先问是否启用知识库模式并选甲/乙知识库（可选）** → P1 锁定最小投标单元 → P2 条款级解析 + 反向漏检 → **P3 选定商务/技术/报价范围** → P4 结构一次性确认 → P5 附件确认 → **P6 确认字数（万字）+ 产出图表规划表（6.0.1 前置门禁）后正文**（防缩水 + 评分权重 + **按图表规划表逐节生成图表：数据类→kami 数据图、流程/结构类→Mermaid；不编造数据**）。
3. 后处理按需：P7 润色去 AI → P8 图表校验/规范化（Mermaid + 数据图） → P9 定稿清理。
4. 交付前：P10 终检/审查通过 + **废标项检查（法定 7 种 + 12 大类 + 一一对应 + `废标项检查报告.pdf`）** → **P11 确认 Word/PDF 输出格式** → 应用排版审美规范 + **表格格式规范（边框/表头样式）** + 字体嵌入导出。
5. 全程不编造、缺失占位 + 待补清单、写盘前确认、终检前不宣称交付。
